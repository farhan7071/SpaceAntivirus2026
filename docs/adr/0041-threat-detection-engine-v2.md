# ADR 0041: Intelligent Threat Detection Engine v2 — six new analyzers, cumulative scoring, confidence

**Status:** Accepted

## Context
Real-device testing through Sprint 026.1 confirmed the app is stable, but the detection engine itself — two analyzers, both permission-combination based — produced nearly identical results regardless of which apps were actually installed. This sprint expands real detection coverage and introduces a genuinely cumulative scoring strategy, without redesigning the pipeline those two analyzers already proved out.

## Decisions

### 1. Six new analyzers, not ten — chosen for what could be built properly, not to hit a number
The brief listed ten candidates. Several (Accessibility Service abuse, VPN applications) require manifest-level `<service>`/`BIND_*_SERVICE` inspection this project's enumerator doesn't currently collect, and adding that data collection reliably wasn't something that could be done with real confidence in this sprint's scope. Excessive background permissions was also set aside — not for a data-availability reason, but to keep this sprint's scope proportionate against the six analyzers below, each of which covers a genuinely distinct evidence dimension rather than a variation on an existing rule. Six were chosen because each is buildable from data already available or from a small, well-justified enumerator extension, each is genuinely conservative (matching the discipline every analyzer in this project has followed since Sprint 014), and each covers a distinct evidence dimension rather than restating an existing rule:

- **`OverlayPermissionAnalyzer`** — `SYSTEM_ALERT_WINDOW` + `INTERNET`. Neither alone; the combination matches real overlay-based credential-harvesting malware.
- **`SurveillanceCombinationAnalyzer`** — `CAMERA` + `RECORD_AUDIO` + `INTERNET`, all three required. The classic "can see, can hear, can transmit" pattern; any two alone describes an ordinary camera or messaging app.
- **`DeviceAdministratorAnalyzer`** — standalone `BIND_DEVICE_ADMIN`, INFO severity, HIGH confidence. Deliberately distinct from `SuspiciousPermissionPatternAnalyzer`'s existing device-admin+INTERNET rule (Sprint 014, ATTENTION severity) — not a duplicate, a different evidence tier for the capability alone versus the combination.
- **`HighRiskPackageNameAnalyzer`** — a non-system app's package name claiming a reserved Android system namespace (`com.android.`, `com.google.android.`, `android.`), exact prefix match only.
- **`DebuggableApplicationAnalyzer`** — `ApplicationInfo.FLAG_DEBUGGABLE` on a non-system app, INFO severity. Requires a new `InstalledApplicationInfo.isDebuggable` field, populated from the same `ApplicationInfo` object already read for `isSystemApp` — no new PackageManager call.
- **`UnknownInstallerSourceAnalyzer`** — `installerPackageName == null`, INFO severity, LOW confidence — the most conservative analyzer in this project, since sideloading and alternative app stores are entirely legitimate reasons to see this. Requires a new `InstalledApplicationInfo.installerPackageName` field, populated via the deprecated but still-functional `PackageManager.getInstallerPackageName()` (stable across API 26–35, this project's full supported range; the newer `getInstallSourceInfo()` was deliberately not adopted purely to avoid API-level branching for zero behavioral benefit within this app's actual range).

Total production analyzers: eight (2 existing + 6 new).

### 2. Duplicate elimination is a natural consequence of existing per-target aggregation, not new merging logic
`RunScanRequestUseCase` already resolves one `ScanTarget` per installed app and runs every registered analyzer against it concurrently; `AnalysisOutcomeAggregator` already combines all of that target's `Detection`s into a single `AnalysisOutcome`, and `BuildThreatUseCase` already builds exactly one `Threat` per target. Adding six more analyzers means more analyzers contribute to that same, already-existing per-app aggregate — it does not require any new merging code. `ThreatBuildingPipelineIntegrationTest`'s new test verifies this directly: an app matching three of the eight analyzers simultaneously, run through the real, fully-registered production pipeline, produces exactly one `Threat` with all three reasons visible. This sprint's "Chrome: Dangerous Permission / Overlay / Unknown Installer → one merged result" example is exactly what that test demonstrates.

### 3. `Confidence` — a new, second axis, distinct from `RiskLevel`
`RiskScorer`'s own KDoc (Sprint 004C) explicitly anticipated this: "a scoring strategy that weighs analyzer confidence, once that concept exists." `Confidence` (LOW/MODERATE/HIGH) represents how sure a specific analyzer is about its specific finding — distinct from `RiskLevel`, which represents how severe the finding would be if true. Added to `Detection` with a default (`MODERATE`) rather than as a breaking change, per this sprint's explicit constraint against breaking architectural changes — dozens of existing `Detection` construction sites across this codebase would otherwise all need updating for a field most have no reason to specify.

### 4. `CumulativeRiskScorer` — a precisely stated escalation rule, not vague "cumulative scoring"
Replaces `HighestSeverityRiskScorer` as the bound `RiskScorer` implementation. `HighestSeverityRiskScorer` itself is unchanged and stays in the project as a genuine, still-valid alternative — exactly what the interface's own documented purpose was for. The rule: never score below the highest individual `RiskLevel` present; escalate to `ACTION_NEEDED` only when two or more **distinct analyzers** (by `analyzerId`, not detection count — a single analyzer producing two detections about the same finding shouldn't be able to escalate itself) each contribute a detection that is **both** at least `ATTENTION` severity **and** at least `MODERATE` confidence. Both conditions matter independently: allowing INFO-level findings (the three new standalone-flag analyzers) or LOW-confidence findings (`UnknownInstallerSourceAnalyzer`) to co-sign an escalation would let genuinely weak evidence push a Threat to the highest severity tier — exactly the "never exaggerate risk" violation (Sprint 002.75 §17) this project has avoided since its first analyzer.

### 5. New `ThreatType.SUSPICIOUS_APP_CONFIGURATION` category
`DeviceAdministratorAnalyzer`, `DebuggableApplicationAnalyzer`, and `UnknownInstallerSourceAnalyzer` findings aren't about *what permissions* an app requests or *who* it claims to be — they're about *how* the app itself is built or installed. Confirmed safe to add before adding it: exactly one exhaustive `when (ThreatType)` exists in this codebase (`ProductionThreatDescriptionProvider`), and the compiler forced real copy to be written for the new case, not just compiled around.

### 6. Device-specific results — satisfied by construction, not new logic
Every analyzer operates on real `PackageManager` data for whatever is actually installed on the device running the scan. Two different phones with different installed apps naturally produce different `InstalledApplicationInfo` lists and therefore different findings — this was already true of the architecture before this sprint. No device-detection or device-branching logic was added, and none was needed; adding it would have been the wrong kind of "device-specific" (branching on device identity) rather than the right kind (results reflecting real, per-device installed-app data).

### 7. Performance — no redundant `PackageManager` calls, confirmed by design
`InstalledApplicationEnumerator.enumerate()` already performs exactly one `PackageManager.getInstalledPackages()` call per scan, producing an immutable `List<InstalledApplicationInfo>` that every analyzer then reads from memory — no analyzer touches `PackageManager` directly, and none ever has. The two new fields (`isDebuggable`, `installerPackageName`) are populated within that same existing enumeration loop, reusing the `appInfo`/`packageInfo` objects already fetched per iteration; `installerPackageName` is the only genuinely new call per app (`getInstallerPackageName`, unavoidable — no field on the already-fetched objects carries this), guarded by its own narrow try/catch since it's documented to throw for certain packages independent of the overall enumeration succeeding.

## Consequences
- Existing tests asserting exact analyzer counts (`AnalysisEngineBindingModuleTest`) were found and updated from two to eight — the same discipline every prior analyzer-count change in this project has followed.
- A future sprint adding manifest-`<service>`-level analyzers (Accessibility Service abuse, VPN applications) will need a real, separate enumerator extension (collecting `PackageInfo.services`) — this sprint deliberately did not attempt that rather than build it without real confidence.
- `HighestSeverityRiskScorer` remaining a real, tested, unbound alternative implementation is a deliberate choice worth remembering if a future sprint wants a "conservative mode" toggle — the substitution point already exists.
