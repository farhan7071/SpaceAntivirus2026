# ADR 0045: Confidence Engine v2 — root cause, design, and what was deliberately left alone

**Status:** Accepted

## Context
Physical-device testing reported well-known, feature-rich applications — named examples: communication, banking, Samsung, and ride-sharing apps — reaching `ACTION_NEEDED` despite expected permission usage. The brief asked for this to be diagnosed from the engine's actual observed behavior, not assumptions, and for any heuristic left unchanged to be explained.

## Root cause, traced through the actual code before any change was made
`CumulativeRiskScorer`'s escalation rule (ADR 0041) — two or more distinct analyzers, each at least `ATTENTION` severity and at least `MODERATE` confidence, escalate together to `ACTION_NEEDED` — was re-read and re-verified, not assumed correct. It is still correct as a rule.

The actual gap: five analyzers currently qualify for this escalation (`SuspiciousPermissionPatternAnalyzer`'s two rules, `AppIdentityImpersonationAnalyzer`, `OverlayPermissionAnalyzer`, `SurveillanceCombinationAnalyzer`, `HighRiskPackageNameAnalyzer`), and three of them — `SuspiciousPermissionPatternAnalyzer`, `OverlayPermissionAnalyzer`, `SurveillanceCombinationAnalyzer` — always reported a flat `Confidence.MODERATE`, regardless of anything else known about the app. These three describe **what an app can do**: permission combinations that legitimate, feature-rich apps routinely need several of at once. SMS for OTP verification, camera/microphone for calls, overlay for chat heads or Samsung's own multi-window features. A communication app requesting SMS+Internet, camera+microphone+Internet, and overlay+Internet all at once isn't exhibiting three independent attack vectors — it's one ordinary app doing ordinary things — but the scorer, working only from severity and a flat confidence, had no way to tell the difference.

This was confirmed by hand-tracing the exact permission set from an existing Sprint 027 test (camera+microphone+overlay+Internet) against all eight analyzers and reasoning through which would fire for each of the brief's named categories — not by guessing at what real communication, banking, Samsung, or ride-sharing apps do.

## Decisions

### 1. The fix lives in the analyzers, not the scorer
`CumulativeRiskScorer` is unchanged — confirmed unchanged in the final diff. Its rule was never wrong; it was starved of the information needed to apply it well. `ConfidenceModulation` (`core:analysisengine`), shared by the three permission-behavior analyzers, lowers confidence one tier when a real, on-device legitimacy signal is present: the app was installed from a known app store (`installerPackageName`, already collected since Sprint 027 — no new data), or the app declares a category consistent with the specific finding (`AppCategory`, already collected since Sprint 028). Two known stores are recognized: Google Play Store (`com.android.vending`) and Samsung Galaxy Store (`com.sec.android.app.samsungapps`) — the second specifically motivated by the "Samsung applications" case in the observed findings. Both signals are OR'd, not summed — a finding matching both is downgraded once, not twice, since both are evidence toward the same underlying question ("is this expected behavior for this app?"), not independently additive facts.

Once a permission-behavior analyzer's confidence drops to `LOW`, `CumulativeRiskScorer`'s own existing "`MODERATE`+ required" rule automatically excludes it from co-escalation — no scorer change needed for that to take effect.

**Why the fix belongs here, not in the scorer:** touching the scorer's threshold or logic would weaken escalation for every analyzer, including the two intentionally left untouched (see below). The actual problem was localized to three specific analyzers reporting an under-informed confidence; fixing it exactly there is "prefer extending existing components over introducing parallel systems," and avoids reasoning about installer/category legitimacy in a place (`CumulativeRiskScorer`) that has no natural business knowing about either.

### 2. Identity-deception analyzers deliberately excluded
`AppIdentityImpersonationAnalyzer` and `HighRiskPackageNameAnalyzer` do not use `ConfidenceModulation`. These reason about **who an app claims to be** (a label matching a known brand with a mismatched package; a package squatting a reserved system namespace) — there is no legitimate reason for either regardless of which store an app came from or what category it declares. Play Store review isn't perfect; malware is occasionally published there. Applying installer trust to these would weaken a genuinely reliable signal for no defensible reason. This is a deliberate non-change, reasoned through and rejected, not an oversight.

### 3. `SurveillanceCombinationAnalyzer`'s existing Sprint 028 suppression is unchanged
Apps declaring `VIDEO` or `SOCIAL` category are still fully suppressed (not just confidence-downgraded) for camera+microphone+Internet — that reasoning (a video-calling app needing this combination isn't a borderline case, it isn't suspicious at all) still holds exactly as written in ADR 0042 and was not revisited. `ConfidenceModulation` only applies to the remaining, non-suppressed path — apps outside those two categories (the ride-sharing case: safety-recording features that may not declare either category) — using installer trust only; category consistency is deliberately not re-checked a second time for this analyzer, since `VIDEO`/`SOCIAL` are already fully handled above it.

### 4. Per-analyzer judgment on which categories are "consistent," not one shared list
`OverlayPermissionAnalyzer` treats `SOCIAL`, `VIDEO`, `PRODUCTIVITY`, and `GAME` as consistent (chat heads, picture-in-picture, multi-window tools, in-game overlays respectively) — a wider set than `SurveillanceCombinationAnalyzer`'s two, because overlay usage is legitimately common across more categories, even though none of them is as unambiguous as "video-calling app needs a camera." `SuspiciousPermissionPatternAnalyzer`'s SMS rule treats only `SOCIAL` as consistent; its device-admin rule treats no category as consistent at all — Android's own category taxonomy has no MDM/enterprise-management category to check against, so only installer trust applies there. Each analyzer's judgment about its own evidence was kept with that analyzer, not centralized into one blanket rule that would have to be right for every case at once.

### 5. Improved reasoning: "why might this still be legitimate," stated explicitly
`ThreatDescriptionProvider.recommendationFor` now appends an explicit sentence when every `Detection` behind a finding has been downgraded to `LOW` confidence, rather than leaving the lower confidence implicit. Deliberately generic about which specific signal applied (installer vs. category) rather than reconstructing that distinction a second time from evidence text — the underlying reasoning is the same either way, and doing so would need `ConfidenceModulation` to return more than a `Confidence` value, a larger change than this sentence needs.

### 6. Confidence transparency: one aggregate label, not per-bullet detail
Each `ThreatSummary` (both `SecurityCenterViewModel` and `HistoryViewModel`) now carries `confidenceLabel` — the highest `Confidence` among the `Threat`'s own `Detection`s, the same "report the strongest signal" precedent `BuildThreatUseCase` already uses for `threatType` selection. Shown in `ThreatSummaryCard`'s expanded state, next to the recommendation. Deliberately a plain `String`, not `core:model`'s `Confidence` type passed through directly — `core:ui` has zero dependency on `domain`/`core:model`, and this preserves that. A per-bullet confidence breakdown was considered and rejected as disproportionate scope for a "where appropriate" requirement — it would have meant restructuring `evidenceBullets` from `List<String>` to a richer type, touching both ViewModels, both screens, and the shared component's core data shape for marginal additional transparency over a single aggregate label.

## What was deliberately not done
- No new `InstalledApplicationInfo` field (target SDK, listed as a *possible* factor in the brief, was not added — `installerPackageName` and `category`, both already available, were sufficient to address every named case).
- No Room schema change anywhere in this sprint — `Detection.confidence` has been persisted since Sprint 029; nothing new needed storing.
- No analyzer removed, no scan coverage reduced, no detection capability weakened for genuinely suspicious apps — confirmed directly: the existing Sprint 027 test proving an app with no legitimacy signal still escalates to `ACTION_NEEDED` was left completely unmodified and still passes.

## A note of honest uncertainty
`com.sec.android.app.samsungapps` (Samsung Galaxy Store) is included with moderate, not full, confidence — it has not been verified against a live device or official Samsung documentation in this sandbox. If incorrect, it is an isolated, one-constant fix in `ConfidenceModulation.kt`; nothing else in this sprint depends on that specific string being exactly right, since Play Store recognition (`com.android.vending`, high confidence) and category-based modulation both function independently of it.

## Consequences
- Every test broken by these changes was found and fixed by direct inspection: three analyzer test files extended with confidence-modulation coverage (not rewritten — all pre-existing tests preserved unchanged, confirming no regression), a new dedicated `ConfidenceModulationTest`, expanded `ProductionThreatDescriptionProviderTest` coverage, and both ViewModels'/screens'/the shared component's tests updated for the new `confidenceLabel` field.
- The single most important test added: a direct sibling to the existing Sprint 027 "three analyzers escalate" integration test, identical in every respect except `installerPackageName`, proving the fix end-to-end through the real production pipeline rather than only at the unit level.
