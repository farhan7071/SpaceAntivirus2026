# ADR 0052: Home Screen Premium UI Polish (Sprint 037)

**Status:** Accepted

## Context
Six numbered, mandatory design corrections against the current implementation, worked through one by one. No ViewModel, repository, scan engine, navigation architecture, or business logic touched — confirmed via exact diff scope. This ADR documents the "before writing code" analysis this sprint explicitly required, and the reasoning behind each of the six fixes.

## A discrepancy in the reference materials, noted before starting
The sprint brief's own numbering ("Image 1 = premium concept," "Image 2 = design system," "Image 3 = design review") didn't match what each image was actually self-labeled as: the image titled "IMAGE 1" was itself labeled "CURRENT IMPLEMENTATION," not a premium concept. Worked from each image's own embedded label rather than the brief's numbering, since that was the more reliable signal. Separately: the design reference image uses a different color palette (`#00E5D1` teal, `#FFC83D` amber) than this project's existing, deliberately-chosen SDS colors. Per this sprint's own "Design Language" section ("use existing color tokens... only introduce new tokens when reusable across multiple screens"), the reference was used for hierarchy, spacing, and composition ideas — not its literal hex values.

## Fix #1 — Hero Card too tall
Outer padding: `spacing.large` (24dp) → `spacing.medium` (16dp). Internal gap: `spacing.medium` → `spacing.small`. Dismiss relocated from inside the result banner to the top-right of the status-label row — a repositioning of existing, real behavior (`onAcknowledgeScanResult`, unchanged), shown only while there's an actual result to dismiss (`ScanUiState.Completed`/`Error`), not new functionality. The large 56dp icon badge beside the headline (a Sprint 036.5 addition) was reconsidered against a clearer look at both reference images — neither actually shows that pattern; both show a small inline icon next to the status label instead. Replaced with that smaller, inline treatment, plus a shrunk (56dp → 44dp) restrained badge alongside the headline/supporting text, deliberately without the reference's own glow/ring illustration — this project's established "avoid decorative effects" discipline (Sprint 036) argues against attempting that literally.

## Fix #2 — Security Summary feels disconnected
`AppStatCard` (Sprint 036) is explicitly designed as "a single labeled statistic in its own compact card" — placing two of them side by side with a gap, as the original Security Summary did, produced exactly "two unrelated cards" by design, not by mistake. Rather than force that component into a layout it isn't meant for, built `AppStatGroup` (new, `core:ui`) — a genuinely reusable sibling that renders multiple stats inside one shared `Card`, separated by `VerticalDivider`s. `AppStatCard` itself is untouched; nothing currently using it changed.

## Fix #3 — Quick Actions too large
Icon badge: 48dp → 36dp. Internal padding: `spacing.medium` → `spacing.small`. The card's own `heightIn(min = LayoutTokens.minTouchTarget)` (48dp) floor is unchanged — the touch target and the icon's own visual size are two different things, and shrinking the latter doesn't compromise the former.

## Fix #4 — Too much vertical spacing
Uniform gap between all four top-level sections: `spacing.large` (24dp) → `spacing.medium` (16dp), an 8dp reduction matching the requested range exactly.

## Fix #5 — Unknown State needs personality
"Protection status unknown" / "Run your first scan to see your protection status" → "Let's get you protected" / "Run your first scan to see how your device is doing." Applied the same reasoning to Recent Activity's own empty state, not only the Hero Card's — "No activity yet. Run your first scan to get started." → "Nothing to show yet — run your first scan and we'll keep you posted here."

## Fix #6 — Scan progress, a real constraint, not just a preference
`ScanProgress` (`core:model`) was verified directly before writing anything: it carries only `itemsProcessed`/`totalItems`/`threatsFoundSoFar` — a linear count, no phase or stage field of any kind. Literally implementing the brief's own example ("Checking installed apps… Analyzing permissions… Scanning app signatures…") would mean displaying a specific, named claim about what the scan engine is doing at a given moment that this presentation-layer code has no way to verify — the same kind of fabrication this project has consistently declined elsewhere (e.g. Sprint 036 not inventing "Apps Scanned" as a persistent Home stat). Modifying the scan engine to genuinely track and report phases would be a business-logic change, explicitly out of this sprint's own scope. Per this sprint's own "Decision Making" section, this doesn't require stopping for approval — it's a presentation-layer adaptation.

Implemented instead: three honest milestones derived directly from the real fraction of items processed — "Starting scan…", "Scanning your apps — N of M checked" (below 50%), "Almost done — N of M apps checked" (50% and above). Every word is something the code can actually verify. `threatsFoundSoFar` is deliberately never surfaced mid-scan — showing a partial, still-accumulating count before `CumulativeRiskScorer` has evaluated the complete picture risks reading as alarming ahead of time, the same "never exaggerate risk" discipline the detection engine itself follows (ADR 0015).

## Design review, round 2 — a real self-correction, and a genuine finding

A follow-up brief asked for a stricter, "would I build it this way from scratch" review of the same screen, rather than incremental polish. Two things came out of it worth documenting honestly.

**A direct correction to my own prior decision.** The brief explicitly states: "do not create reusable components unless two or more screens genuinely need them today." Round 1 of this sprint extracted `AppStatGroup` to `core:ui`, justified by "a future sprint touching Security Center is a reasonable place to consider adopting this too" — that's hypothetical reuse, not a genuine need today. Verified directly (not assumed): nothing else in the codebase called it. Removed `AppStatGroup.kt` and its test entirely, and folded the same visual behavior back into `HomeScreen.kt` as simple, local presentation code (`SecuritySummarySection` building a `Card` + `VerticalDivider` directly, `SecurityStat` as a small private composable) — not a generic `StatGroupItem` data class either, since there's exactly one caller and that indirection wasn't warranted for it. This is a genuine reversal of a design-system decision made one round earlier, not just an addition on top of it.

**A real finding in the design system itself, not invented for this sprint.** Re-reviewing the Hero Card against "would this feel like a product identity, not a Material Card / Icon / Button" led to actually reading `Type.kt`'s own KDoc closely: `displayLarge` is documented as "reserved for exactly the two hero moments (status headline, scan-complete moment)." This exact headline — "You're protected" / "Attention needed" / "Let's get you protected" — *is* that status headline, and across two entire prior rounds of Hero Card polish, it had never actually used `displayLarge`; `headlineSmall` (24sp) was used instead throughout. The design system's own typography scale already had the right, deliberate answer for "unmistakably the primary focus" before this round asked the question — it simply hadn't been applied. Switched the headline to `displayLarge`, and removed the separate restrained icon badge (44dp, from round 1) that had sat beside it — at `displayLarge`'s scale, a second icon element competed with the headline rather than reinforcing it. The small, accessible icon in the status-label row above the headline (unchanged) still carries the icon role.

A real implementation mistake was also caught and fixed during this round: an `str_replace` that updated `SecuritySummarySection`'s function body left its old KDoc comment and a stray duplicate `@Composable` annotation in place above the new one — two KDoc blocks and two `@Composable` annotations stacked before one function, which would not have compiled. Caught via a direct, automated scan for exactly this pattern before finalizing, not left for a build to discover.

## Consequences
- Net result across both rounds: `AppStatGroup.kt` and its test were added, then removed in the same sprint once round 2's stricter review caught the premature abstraction — the final delivered state has no new `core:ui` component from this sprint at all, only presentation-layer changes to `HomeScreen.kt` itself.
- `HomeScreenTest.kt` needed zero changes across round 2 — the headline's text content, and every stat's value/label text, are unchanged; only their typography style and underlying component structure changed.
- `AppStatCard`'s own file remains completely untouched throughout both rounds.
