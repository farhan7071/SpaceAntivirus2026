# ADR 0046: Context-Aware Detection Intelligence

**Status:** Accepted

## Context
This sprint's brief named three classes to review before making any changes — `PermissionCombinationAnalyzer`, `OverlayBehaviorAnalyzer`, `SmsBehaviorAnalyzer` — none of which exist in this codebase under those names. Verified against a genuinely fresh clone before any other work: this project's actual analyzer classes are `SuspiciousPermissionPatternAnalyzer` (handles the SMS+Internet and device-admin+Internet rules together — there is no separate SMS-only analyzer), `OverlayPermissionAnalyzer`, and `SurveillanceCombinationAnalyzer`. The brief's own instruction — "Do not assume anything. Work only from the current repository" — was followed literally: rather than guessing at a rename that never happened, this ADR documents the mapping explicitly and all work proceeds against the real classes.

`ConfidenceModulation`, `ProductionThreatDescriptionProvider`, and `CumulativeRiskScorer` were each read in full before any change, confirming Sprint 031's design (ADR 0045) is present and unmodified by anything between then and now.

## Decisions

### 1. Two more real, already-populated `AppCategory` values put to use
`AppCategory` mirrors Android's own `ApplicationInfo.CATEGORY_*` taxonomy exactly (ADR 0042) — nine values, already collected on every scan since Sprint 028. Two of them, `AUDIO` and `MAPS`, were never checked by any analyzer's `categoryIsConsistent` logic despite being real, on-device data. Both are now added to `OverlayPermissionAnalyzer`'s consistent-category set: `AUDIO` for floating media-playback controls (a common, legitimate overlay use on music apps), `MAPS` — Android's actual "Maps & Navigation" Play Console category — for navigation/ride-sharing apps showing turn-by-turn directions as an overlay while the user is in another app. Neither required new data collection or a new field; both were sitting unused.

`SurveillanceCombinationAnalyzer` gained `IMAGE` as a category-consistency signal for camera apps and photo editors — deliberately added to the confidence-*downgrade* path (`ConfidenceModulation`), not the existing `VIDEO`/`SOCIAL` *suppression* set. A pure photo editor doesn't inherently need `RECORD_AUDIO` the way a video-calling app inherently needs it, so this is a genuinely weaker legitimacy signal than the suppression case — exactly the distinction a confidence downgrade exists to express and an outright suppression can't. The `VIDEO`/`SOCIAL` suppression itself, and its Sprint 028/031 reasoning, is completely unchanged.

### 2. What Android's own taxonomy genuinely can't distinguish
The brief additionally named banking apps, wearable companion apps, and smart-home apps as categories needing recognition. Android's `ApplicationInfo.CATEGORY_*` constants — which `AppCategory` mirrors exactly, on purpose, so this project is never inferring a classification the OS itself didn't make — have no finance, wearable, or smart-home category. Inventing new `AppCategory` values not backed by any real Android constant would mean this project claiming to read a classification that doesn't exist on the device, which is precisely the kind of unsupported signal this project has avoided since `AppCategory` was first introduced. For these three app types, installer trust (`ConfidenceModulation`'s other, category-independent signal) remains the only applicable legitimacy signal — documented as a genuine platform limitation, not worked around with invented data.

### 3. No changes to `CumulativeRiskScorer` — cross-analyzer reasoning satisfied by construction
The brief's "cross-analyzer reasoning" requirement (multiple analyzers triggering from the same expected functionality shouldn't amplify concern) is already satisfied by Sprint 031's design, extended slightly further here: `CumulativeRiskScorer`'s existing "two or more distinct analyzers, each `MODERATE`+ confidence, escalate together" rule (ADR 0041, unchanged again this sprint) means that as more permission-behavior analyzers correctly recognize a specific app's category as consistent, more of that app's findings drop below the escalation threshold independently — no analyzer needs to know about any other analyzer's decision. A communication app triggering camera+microphone (now recognized for `SOCIAL`/`VIDEO`, and via installer trust for anything else) and overlay (now recognized for `SOCIAL`/`VIDEO`/`AUDIO`/`MAPS`/`PRODUCTIVITY`/`GAME`) naturally has both findings downgraded together, without either analyzer being aware the other fired. This is not a new mechanism — it is the existing Sprint 031 mechanism doing more useful work because more of its inputs are now correctly informed.

### 4. Broadened, honest recommendation wording — not invented specificity
`ThreatDescriptionProvider.recommendationFor`'s three evidence-keyed branches (camera/microphone, overlay, SMS) now each name several plausible legitimate app types instead of one generic phrase — communication, video calling, and ride-sharing verification for the camera/microphone branch; media controls, picture-in-picture, navigation, and chat heads for overlay; messaging and banking authentication for SMS. This method only ever receives `evidenceDescription` text and a `Confidence` value — it has no access to the app's actual declared category or installer, both of which are already spent by the time confidence reaches it. Naming one specific app type as *the* explanation ("this is a banking app") would be inventing certainty the method genuinely doesn't have; naming several real categories the pattern is expected for is the honest version of "balanced explanation" available at this layer. Every existing test's required substring (`"calls or media"`, `"overlay access"`, `"SMS access"`) was verified preserved before this change was finalized, not assumed.

### 5. Transparency preserved unchanged
`confidenceLabel` (Sprint 030/031) and the "why might this still be legitimate" sentence (Sprint 031) are untouched — both already satisfy "never hide the reason," and this sprint's changes only feed them more accurately informed inputs, not new mechanisms.

## Regression guarantees, verified structurally and behaviorally
- `AppIdentityImpersonationAnalyzer.kt` and `HighRiskPackageNameAnalyzer.kt` (the two identity-deception analyzers `ConfidenceModulation` was already designed to exclude, ADR 0045) — their *main* source files are untouched this sprint, confirmed via exact diff scope. New tests added to each proving this holds behaviorally, not just in the diff: both analyzers report their original, unmodified confidence (`MODERATE` and `HIGH` respectively) even when installed from the Play Store — an app claiming a false identity or squatting a reserved namespace has no legitimate excuse regardless of distribution channel.
- `ThreatBuildingPipelineIntegrationTest.kt`, `ConfidenceModulation.kt`, `SuspiciousPermissionPatternAnalyzer.kt`, and `CumulativeRiskScorer.kt` are all untouched this sprint, confirmed via exact diff scope — the existing Sprint 027/031 test proving a genuinely suspicious app with no legitimacy signal still escalates to `ACTION_NEEDED` was never modified and continues to pass unchanged.

## Consequences
- 8 files changed, all within `core/analysisengine`. No new analyzer, no UI file, no Room file, no file outside the analyzer/reporting layer this sprint's brief scoped work to.
- A future sprint wanting to recognize banking, wearable, or smart-home apps more precisely would need either a genuinely new, well-justified data source beyond `ApplicationInfo.category` (not something this project should invent casually) or acceptance that installer trust is the practical ceiling for those categories on this platform.
