# ADR 0042: Threat Intelligence Refinement — false-positive fixes, no new analyzers

**Status:** Accepted

## Context
Real-device testing of Sprint 027's eight analyzers reported five concrete quality issues, none of which called for more detection coverage — the opposite: "overall detection quality is good, but false-positive resistance should improve before introducing additional analyzers." This sprint fixes three real, root-caused issues in existing analyzers and adds zero new analyzers, per that explicit instruction. No architectural change was made anywhere it wasn't required to fix one of these issues.

Before writing any code, two claimed prior "integration fixes" (relocating `ScanTarget.identifier` to `core:model`, and a `FileTreeWalker` hidden-file/dot-file fix) were verified directly against the actual commit history rather than accepted at face value — both are genuinely present and were understood by reading their real diffs before being treated as baseline.

## Decisions

### 1. `HighRiskPackageNameAnalyzer`: removed `com.google.android.` from reserved namespaces
This was a genuine design mistake in Sprint 027, not a hardening opportunity — the namespace is not exclusively reserved for pre-installed system components the way `com.android.` and `android.` are. Many entirely legitimate, Play-Store-distributed Google apps use it (Gmail, YouTube, Maps), and critically, `isSystemApp` only reflects whether an APK currently lives in the read-only system partition — a Google app updated via the Play Store after first boot commonly becomes `isSystemApp = false` while remaining completely genuine. The `isSystemApp` exclusion this analyzer already had could never protect against this, since the apps most likely to trip the rule were exactly the ones no longer flagged as system apps. `com.android.` and `android.` don't share this problem — Play Store signing policy doesn't permit ordinary or even Google-published apps to use those specific namespaces, making them a genuinely reliable signal on their own, unlike the one removed.

### 2. `DeviceAdministratorAnalyzer`: excluded apps that also have `INTERNET`
The real cause of "some applications generate multiple repetitive findings": this analyzer and `SuspiciousPermissionPatternAnalyzer`'s existing device-admin+INTERNET combo rule (Sprint 014) could both fire on the same app, producing two separate findings about essentially the same underlying fact, worded differently. `AnalysisOutcomeAggregator`'s dedup (Sprint 015) is exact-match by design and cannot and should not be made fuzzier to collapse this — genuinely different findings must stay genuinely different. The fix belongs at the analyzer level: `DeviceAdministratorAnalyzer`'s own reason to exist is catching device-admin apps the combo rule can't see (no `INTERNET` permission at all); once an app has both, the combo rule already covers it more specifically and at higher severity, so this analyzer now stays silent rather than adding a redundant, lower-severity echo.

### 3. `SurveillanceCombinationAnalyzer`: category-aware suppression, not softened wording
Addresses "some permission combinations should include contextual explanations... expected for certain categories of legitimate applications." Rather than adding caveat text to a finding that fires regardless, apps declaring `ApplicationInfo.CATEGORY_VIDEO` or `CATEGORY_SOCIAL` — a real, developer-declared, Play Store–facing classification, not this project inferring anything — are excluded entirely. A video-calling app legitimately needing camera+microphone+internet isn't a borderline case worth a gentler warning; it isn't suspicious at all, and not flagging it is more honest than flagging it with a caveat attached. This is a binary suppression, not a confidence adjustment — a category is either a real, positively-identified fact (skip) or it isn't (evaluate normally); no middle state exists.

### 4. New `AppCategory` model, mapped from a real, stable Android API
`ApplicationInfo.category` has existed since API 26 — this project's exact `minSdk` (ADR 0003) — so no API-level branching was needed anywhere it's read. Mapped via `ApplicationInfo`'s own named `CATEGORY_*` constants, not guessed raw integer values, eliminating any risk of an incorrect mapping. `InstalledApplicationInfo.category` defaults to `AppCategory.UNDEFINED`, following the same non-breaking pattern Sprint 027 established for `isDebuggable`/`installerPackageName` — populated within the enumerator's existing single enumeration loop, no new `PackageManager` call.

### 5. What was deliberately not done
No new analyzers were added, per Issue 5's explicit instruction. `AppIdentityImpersonationAnalyzer`'s brand-matching logic was reviewed but left unchanged — its exact-label-match requirement already provides meaningful protection against the kind of false positive `HighRiskPackageNameAnalyzer` had, and the real-device report's wording ("package-name heuristics") points specifically at the purely-package-name-based analyzer, not the label+package analyzer. `AnalysisOutcomeAggregator`'s dedup logic was reviewed and deliberately left untouched — broadening exact-match dedup to catch conceptually-related-but-differently-worded findings would risk silently collapsing genuinely distinct evidence from other analyzer pairs; the real fix belonged in the one analyzer whose design created the overlap, not in shared aggregation logic every analyzer depends on.

## Consequences
- One existing test (`HighRiskPackageNameAnalyzerTest`'s `com.google.android` coverage) was found and replaced with a test verifying the actual fix — the same discipline every prior analyzer-behavior change in this project has followed, not left to surface as a silent behavioral drift.
- `CumulativeRiskScorer`'s escalation rule (ADR 0041) is unaffected by any of these changes — `DeviceAdministratorAnalyzer`'s narrower firing conditions and `SurveillanceCombinationAnalyzer`'s category suppression both reduce the set of detections reaching the scorer, but neither changes how the scorer reasons about whatever detections do arrive.
- A future sprint wanting category-aware suppression for other analyzers (e.g. `OverlayPermissionAnalyzer` for legitimate accessibility/utility apps) now has a working, tested pattern to follow — `AppCategory` and the enumerator support for it already exist.
